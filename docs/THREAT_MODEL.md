# Модель угроз MikroTik Route Sync

## Обзор

Документ описывает потенциальные угрозы безопасности для системы MikroTik Route Sync и применяемые контрмеры. Система спроектирована для работы в доверенной домашней/LAN-сети (Proxmox LXC, ≤128 МБ RAM) и управляет критичной сетевой инфраструктурой — маршрутизацией на MikroTik RouterOS.

**Важно:** проект работает **только с IPv4**; префиксы IPv6 отбрасываются на этапах сбора и валидации.

## Активы

1. **Конфигурация** — содержит пароли, токены, ключи API
2. **Маршруты MikroTik** — критичная сетевая инфраструктура
3. **Данные кэша (bbolt)** — ASN/WHOIS/RDAP результаты, снапшоты, история
4. **Логи** — могут содержать чувствительную информацию
5. **Telegram-бот** — канал управления и уведомлений
6. **Web UI / REST API** — канал управления

## Угрозы

### 1. Несанкционированный доступ к конфигурации

**Угроза:** Злоумышленник получает доступ к `config.yaml` и извлекает пароли/токены.

**Вероятность:** Средняя

**Влияние:** Высокое

**Контрмеры:**
- Права файла `0600`, проверка при старте и отказ запуска (на POSIX; отключение через `MRS_REQUIRE_FILE_PERMS=0` для специфичных окружений вроде Docker Desktop)
- Файл добавлен в `.gitignore` и `.dockerignore`
- Маскирование секретов в CLI/Web (только последние 4 символа)
- Секреты можно выносить в ENV (`MRS_MIKROTIK_PASSWORD`, `MRS_TELEGRAM_BOT_TOKEN`, `MRS_WEB_PASSWORD`)
- Redaction секретов в логах и в сообщениях об ошибках

### 2. Подмена/порча конфигурации при записи

**Угроза:** Повреждение `config.yaml` при записи (крах, гонка двух процессов) или подмена значений.

**Вероятность:** Низкая

**Влияние:** Критическое

**Контрмеры:**
- Атомарная запись: tmpfile + fsync + rename, права 0600
- Полная валидация конфигурации перед сохранением и перед применением
- Все изменения через веб/UI логируются в аудит без значений секретов

### 3. SSRF через внешние API и пользовательские URL

**Угроза:** Злоумышленник (или скомпрометированный источник) заставляет систему обращаться к внутренним ресурсам: роутер, гипервизор, metadata-эндпоинты.

**Вероятность:** Средняя

**Влияние:** Высокое

**Контрмеры:**
- Только `http/https` схемы; проверка URL из overrides при загрузке конфига
- SSRF-guard в транспортном слое: блокировка private/loopback/link-local/multicast адресов на этапе dial
- Ограничение редиректов (≤3) с проверением схемы цели
- Ограничение размера ответа (`io.LimitReader`, `external.max_response_mb`)
- Таймауты на все внешние запросы

### 4. Отказ в обслуживании (DoS) приложения

**Угроза:** Перегрузка Web UI/API частыми запросами, исчерпание ограниченных ресурсов LXC.

**Вероятность:** Средняя

**Влияние:** Среднее

**Контрмеры:**
- Rate limiting на IP (golang.org/x/time/rate)
- Ограничение тела запроса ≤1 МБ (`http.MaxBytesReader`)
- Таймауты HTTP-сервера (Read/ReadHeader/Idle)
- Ограничение параллельности синхронизаций (`scheduler.max_concurrent`, mutex на сервис)
- Circuit breaker на каждый внешний хост
- Лимиты ресурсов контейнера (128 МБ / 1 CPU)

### 5. Массовое удаление маршрутов (главная угроза целостности сети)

**Угроза:** Ошибка/компромисс источника приводит к пустому или аномальному набору CIDR и удалению рабочих маршрутов.

**Вероятность:** Средняя

**Влияние:** Критическое

**Контрмеры:**
- Fail-closed: пустой результат источника = ошибка, маршруты не изменяются
- Safe-diff: `deleted / existing > max_delete_ratio` (0.5) блокирует синхронизацию до `--force`
- Абсолютный порог `require_confirmation_over`
- Агрегация с проверкой инвариантов (сумма адресов и покрытие) и безопасным откатом
- Snapshot в bbolt перед каждой операцией; rollback при сбое применения
- Порядок применения: сначала добавление, затем удаление (zero-downtime)

### 6. Компрометация Telegram-бота

**Угроза:** Сторонний пользователь управляет синхронизацией или получает статус сети.

**Вероятность:** Низкая

**Влияние:** Высокое

**Контрмеры:**
- Авторизация только по `authorized_chat_ids`; остальные игнорируются без ответа
- Rate limit сообщений на chat_id
- Попытки доступа логируются с `WARN`
- В уведомлениях не передаются секреты (redaction)

### 7. Утечка секретов через логи/API

**Угроза:** Пароли/токены попадают в логи, ответы API, сообщения Telegram.

**Вероятность:** Средняя

**Влияние:** Высокое

**Контрмеры:**
- Centralized redaction в slog (`ReplaceAttr`): password, token, secret, key, authorization, cookie, session
- Ограничение тела ответа RouterOS в ошибках + regex-redaction перед логированием
- `retryablehttp.Logger = nil` (заголовки, включая Authorization, не логируются)
- Маскирование в настройках Web UI, `config get` в CLI, уведомлениях

### 8. Man-in-the-Middle (MITM)

**Угроза:** Перехват трафика между приложением и MikroTik/внешними API.

**Вероятность:** Низкая (в домашней сети)

**Влияние:** Высокое

**Контрмеры:**
- TLS 1.2+; `verify_ssl: true` по умолчанию (при false — предупреждение в лог)
- HSTS при HTTPS на Web UI
- Рекомендация: доверенный сертификат на RouterOS и ограничение API-пользователя по IP

### 9. Атака на Web UI: CSRF, кликджекинг, brute-force

**Угроза:** Межсайтовая подделка запросов к API с авторизованной сессии браузера; подбор пароля.

**Вероятность:** Средняя

**Влияние:** Высокое

**Контрмеры:**
- CSRF-токен для всех изменяющих запросов (кроме чисто Basic-auth, невосприимчивого к CSRF)
- Session cookie: HttpOnly, SameSite=Strict, TTL
- Constant-time сравнение пароля (`crypto/subtle`)
- Security headers: CSP (без unsafe-inline/unsafe-eval), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`
- `allowed_cidrs` — слушать и пускать только LAN/VPN
- Rate limiting на IP

### 10. Инъекции в RouterOS

**Угроза:** Специальными символами в именах сервисов/комментариях сломать запрос или комментарий RouterOS.

**Вероятность:** Низкая

**Влияние:** Высокое

**Контрмеры:**
- Валидация имени сервиса `^[a-z0-9][a-z0-9_-]{0,63}$`
- Экранирование-запрет `"`, `\`, `\n`, `\r` в комментариях
- Валидация `.id` маршрута перед DELETE (без `/ ? #`)
- Все операции — только со своими `AUTO:<service>` маршрутами (двойная фильтрация: запрос + клиентская проверка)

### 11. Злоупотребление расписаниями

**Угроза:** Невалидное/циклическое расписание вызывает шторм синхронизаций и запросов к внешним API.

**Вероятность:** Низкая

**Влияние:** Среднее

**Контрмеры:**
- Валидация формата расписания при загрузке и через API
- Mutex на сервис (наложение запусков пропускается с WARN)
- Ограничение `max_concurrent`, лимит времени синхронизации (10 мин)
- Rate limit запросов к RouterOS (`mikrotik.rate_limit`)

### 12. Supply chain

**Угроза:** Вредоносная или уязвимая транзальная зависимость.

**Вероятность:** Низкая

**Влияние:** Высокое

**Контрмеры:**
- 11 прямых зависимостей, все — мейнстрим-пакеты; `go.sum` зафиксирован
- Перед релизом: `govulncheck ./...`, `gosec ./...`
- Статический бинарник `CGO_ENABLED=0`, `-trimpath`, `-s -w`
- Non-root контейнер, `cap_drop: [ALL]`, `no-new-privileges`, read-only rootfs

## Допущения модели

- Домашняя/LAN сеть считается частично доверенной; прямой публикацией портов в интернет пренебрегать нельзя (Web UI по умолчанию только 127.0.0.1).
- Владелец хоста с `config.yaml` считается доверенным (файл хранит секреты в открытом виде).
- Источники данных (bgp.tools, RIPEstat, CDN-списки) — внешние и потенциально враждебные: им не доверяем, данные проходят многоуровневую валидацию и safe-diff.
